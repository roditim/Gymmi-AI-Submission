# Gymmi — מה בנינו ואיך להסביר

Gymmi עוזר למתאמן לתכנן אימונים בשבוע, לרשום מה השלים ולראות התקדמות. לדוגמה: מתכננים שלושה אימונים במחשב, פותחים את אותו חשבון בטלפון אחרי האימון הראשון, מסמנים ״הושלם״ ורואים אחד מתוך שלושה. זהו כלי ארגון ומעקב בסיסי.

## התאמה לאישור יונתן

בהודעה הראשונה יונתן אישר כיוון שכלל CrewAI, Flow וחיזוי והדגיש Scope צר: תוכנית והתקדמות בסיסית, עם RPG כהרחבה. בהבהרה המאוחרת יותר שסופקה בשיחה הוא קבע ש־CrewAI הוא המלצה, מודל מאומן אינו חובה, וחובה שהאפליקציה תעבוד באינטרנט בקישור ציבורי. ההבהרה המאוחרת מנחה את גרסת ההגשה.

| מה נאמר | מה יש בפרויקט |
|---|---|
| רעיון Gymmi מתאים | ארגון תוכנית אימונים והתקדמות |
| Scope צר | הוספה, עריכה, סימון השלמה/דילוג, היסטוריה וגיבוי |
| Production ציבורי חובה | ממשק GitHub Pages עם קישור HTTPS ציבורי |
| CrewAI המלצה בלבד | אינו מופעל במוצר הציבורי; מחקר קודם נשמר בנפרד |
| ML מאומן אינו חובה | אין חיזוי במוצר ואין טענת דיוק על השלמת אימון |
| RPG יכול להישאר הרחבה | לא נכלל ב־MVP |
| חשבונות לא הוגדרו כחובה | Supabase נוסף לבקשת המשתמש, לשמירה בין מכשירים |

לפי הטקסט שסיפקת, ההיקף הזה תואם להבהרה האחרונה. אין כאן אישור נפרד של המרצה למימוש המסוים או הבטחה לציון. שם הפרויקט נשאר Gymmi AI, אך צריך לומר במפורש שהמוצר הפעיל כרגע הוא מעקב אימונים ואינו מייצר תוכנית באמצעות AI.

## מה עשינו

1. פרסמנו ממשק ציבורי פשוט, עם HTML, CSS ו־JavaScript.
2. בנינו תוכנית שבועית: שם אימון, תאריך, דקות מתוכננות ותרגילים שהמשתמש מזין.
3. הוספנו השלמה, דילוג וביטול סימון. אימון שלא סומן נשאר לא ידוע; לא מניחים שהמשתמש נכשל.
4. חישבנו התקדמות: מספר שהושלמו חלקי מספר האימונים בשבוע. זו ספירה, לא מודל ML.
5. שמרנו מצב אורח בדפדפן, עם גיבוי JSON ואימות קבצים.
6. הקמנו פרויקט Supabase נפרד בשם Gymmi בארגון במסלול Free, באזור Frankfurt. לא שינינו פרויקטים קיימים ולא הופעלו תוספים בתשלום.
7. הוספנו טופס הרשמה וכניסה במייל וסיסמה, יציאה, ושמירת היומן של החשבון בענן. באישור מפורש מ־4.11.2026, ההרשמה מכניסה מיד לחשבון ללא אימות בעלות על המייל.
8. הוספנו בדיקת גרסה למניעת דריסת עדכון ממכשיר אחר והרשאות במסד לבידוד חשבונות.

## איפה הקוד

| קובץ | מה להסביר |
|---|---|
| docs/app/index.html | הטפסים, מסכי התוכנית, היסטוריה וגיבוי |
| docs/app/style.css | צבעים, מרווחים והתאמה לטלפון |
| docs/app/app.js | תגובה לפעולות, בדיקת נתונים, מצב המסך וספירת ההתקדמות |
| docs/app/cloud.js | שתי פעולות עיקריות: load לקריאה ו־save לשמירה |
| docs/app/config.js | כתובת Supabase ומפתח ציבורי; אין כאן סיסמת מסד או מפתח מנהל |
| supabase/migrations/20261104075112_cloud_journals.sql | הטבלה ומדיניות הגישה |
| tests/browser_mvp.cjs | בדיקות מצב אורח בדפדפן |
| tests/cloud_mvp.cjs | בדיקות עם חשבונות QA זמניים מול הענן |

app.js ארוך יותר כי הוא כולל גם פעולות ממשק וגם טיפול בכשלים, אך אין בו framework או מערכת מחלקות. ההפרדה העיקרית היא בין המסך לבין תקשורת הענן ב־cloud.js. ספריית Supabase היא קוד חיצוני עם רישיון; לא צריך להסביר את המימוש הפנימי שלה כאילו כתבת אותו.

## מה נשמר במסד

בטבלה workout_journals יש שורה לכל חשבון: user_id, רשימת workouts בפורמט JSON, ומספר revision. בכל אימון יש מזהה, תאריך, כותרת, דקות, פרטים, סטטוס וזמן סימון. בחרנו לשמור יומן שלם כדי להשתמש באותו מבנה פשוט של גיבוי ומצב אורח. זה מתאים ל־MVP קטן; יש מגבלה של 1,000 אימונים ו־1MB ליומן. מפתחות ותוכן חשבונות אינם נשמרים בריפו.

בעת שמירה, הלקוח שולח גם את מספר הגרסה שקרא. העדכון מצליח רק אם הגרסה במסד עדיין זהה. אם מכשיר אחר שמר קודם, העדכון נדחה. המשתמש יכול לשמור את פרטי הטיוטה, לטעון מחדש ולערוך שוב. אין מיזוג אוטומטי ואין Realtime: מרעננים או לוחצים ״טען מחדש מהענן״.

## למה משתמש לא רואה אחרים

Supabase Auth בודק את הסיסמה ומנפיק Session. הדפדפן אינו שומר את הסיסמה של המשתמש בקוד או ביומן. במסד פועלת RLS: אפשר לקרוא, ליצור ולעדכן שורה רק כאשר auth.uid() תואם ל־user_id. הבדיקה נעשית גם במסד, כך ששינוי JavaScript בדפדפן אינו עוקף אותה. נבדקו בקשות API ישירות מחשבון אחר, כולל ניסיון לשנות בעלות על שורה.

מפתח publishable באתר הוא מזהה ציבורי שנועד לדפדפן; ההרשאות ו־Session מגינים על השורות. מפתח service/secret וסיסמת המסד אינם נכללים באתר. כמו באפליקציות דפדפן אחרות, יש לצאת מהחשבון במחשב משותף ולא להזין מידע רפואי רגיש ב־MVP הלימודי.

## איך מונעים שמירה מטעה

המסך מתעדכן רק אחרי אישור שמירה. בזמן פעולה נחסמים לחצני עריכה כפולים. בכשל רשת התוכן השמור נשאר והטיוטה בטופס נשמרת. אם טעינת הענן נכשלת, העריכה חסומה עד טעינה מוצלחת; לא פותחים יומן ריק שעלול לדרוס מידע. החלפת חשבון מנקה מיד את היומן המוצג לפני טעינת החשבון הבא.

## אורח וחשבון הם שני יומנים

אין העלאה אוטומטית של אימוני הדפדפן. אחרי כניסה אפשר ללחוץ ״העבר יומן מקומי לחשבון״ ולאשר החלפה. העותק המקומי נשאר כגיבוי. יציאה מחזירה למצב אורח. ייבוא גיבוי או איפוס בזמן כניסה משפיעים על היומן בענן, ולכן מוצגת בקשת אישור.

## מה עדיין פתוח

- באישור המשתמש ל־MVP הלימודי, אין אימות מייל: אפשר להזין גם כתובת שאינה בבעלות הנרשם. אין ספק SMTP ואין שחזור סיסמה באתר.
- בדיקות הענן הוותיקות השתמשו בחשבונות בדיקה שאומתו דרך כלי ניהול. בדיקת ההרשמה החדשה מפעילה את הטופס הציבורי ללא אישור מנהל. חשבונות QA נמחקים בסוף; אין מסירת מייל ואין טענה שהכתובת אומתה.
- אין אימות אנושי עצמאי או הבטחה לציון. ההגשה למרצה לא נשלחה מתוך הפרויקט.
- Free עשוי להשהות פרויקט אחרי פעילות נמוכה במשך שבוע. יש לבדוק זמינות לקראת ההצגה; לא הופעל מסלול בתשלום.
- אין יצירת תוכנית אישית אוטומטית, AI פעיל, RPG, המלצות רפואיות או חיזוי השלמה. אלה אינם נדרשים לפי ההבהרה המאוחרת שסיפקת.
