# איך להסביר את Gymmi בהגשה

מדריך להבנת הקוד ולתרגול ההסבר. הוא אינו הצהרה שהסטודנט כתב כל שורה לבד
או שכבר יודע להסביר אותה. נעשה שימוש בעוזר קוד, כפי שהודגם בקורס.

## מה המערכת עושה

Gymmi משווה מודלים לחיזוי ביקור כלשהו בשבוע הבא לפי ארבע ספירות של ביקורים קודמים.
המשתמש רואה את הנתונים, את ההשוואה ואת הסיבה לעצירה בכשל.
היעד הוא week2 > 0. אין במקור נתוני הזמנות לשיעורים.

## המסלול של הקוד

1. `run.py` קורא פרמטרים מהטרמינל ומפעיל את ה־Flow.
2. `analyst.py` מנקה נתונים, יוצר EDA ומפרסם חוזה נתונים.
3. `boundary.py` בודק שהקובץ מתאים לחוזה לפני שממשיכים.
4. `scientist.py` מכין תכונות ומשווה Logistic Regression ו־Random Forest.
5. `feature_gate.py` בודק שהתכונות מתאימות לנתונים ולפיצול שהוגדרו.
6. `artifact_status.py` מאשר חיזוי רק אחרי השלמת התוצרים והבדיקות.
7. `app.py` מציג את התוצאות ב־Streamlit; `prediction.py` מפעיל את החיזוי.

`crews.py` מחלק את העבודה לשני crews של שלושה סוכנים, עם כלי מוגדר לכל תפקיד.
`reviews.py` מגדיר את מבנה הסקירה ובודק שהטענות מתאימות לראיות.
`config.py` טוען הגדרות מתוך `.env`, כמו בדוגמאות הקורס.

## הקשר לחומרי הקורס

| רעיון | המקור בקורס |
|---|---|
| פונקציות, מחלקות, חריגות וקבצים | Python |
| ניקוי, חסרים, תרשימים ו־EDA | Data Science |
| train/validation/test והשוואת מודלים | Data Science ופרויקט הגמר |
| Agent, Task, Tool, Pydantic ו־Flow | NewsDesk, Agents ודוגמת הגמר |
| `.env` ו־`load_dotenv` | `sol_Example/main.py` של NewsDesk |

| ענף, commit ו־PR | תרגיל Git ו־GitHub |

המיפוי מבוסס על עיון בחומרי הקורס הפרטיים. קבצי הקורס והקישורים הפרטיים אינם חלק מההגשה הציבורית.

## הסברים שכדאי לתרגל

- **למה לא למלא חסרים על כל הנתונים?** כך מידע מה־test עלול להיכנס להכנת
  המודל. מתאימים preprocessing ל־train בלבד.
- **למה validation וגם test?** ב־validation בוחרים מודל וסף. ה־test משמש
  להערכה; כאן הוא נחשף בפיתוח, ולכן אינו ניסוי עיוור חדש.
- **מה הסוכנים עושים?** מפעילים כלים מוגדרים וכותבים סקירה לפי הראיות.
  החישובים והאימון נעשים ב־Python, ולא בניחוש של מודל השפה.
- **מה קורה אם קובץ שגוי?** מעלים חריגה, שומרים כשל ועוצרים בשלב המתאים.
- **למה checksum וגם בדיקת ערכים?** הראשון מזהה שינוי בקובץ, והשנייה בודקת
  שהתכונות חושבו לפי הכללים. אלה אינן הוכחות לאמיתות המקור.
- **למה `SUCCESS.json`?** קובץ מודל לבדו אינו מוכיח שכל הריצה הושלמה.
  האישור קושר את התוצרים, וחיזוי דורש שהם עדיין מתאימים.
- **מה ההבדל בין offline ל־live?** ב־offline כלים אמיתיים מופעלים עם תשובות
  בדיקה כתובות מראש. רק ב־live נעשות קריאות לספק LLM.

## היקף קטן במכוון

ממשק Streamlit אחד, CSV, שני מודלים נלמדים ושני crews. אין צורך ב־RPG,
microservices, Kubernetes, זיכרון סוכנים או RAG. שערי האימות נשארים כי הם
חלק ממטרת הפרויקט ומדוגמת המרצה. אין להוסיף רכיב רק כדי להציג עוד טכנולוגיה.

להתכונן להצגה לפי סדר הקוד, ואז להריץ הצלחה וכשל ולהסביר את ההבדל.
חלק שאינו ברור צריך ללמוד או לפשט לפני ההגשה, תוך תיאור כן של העזרה בקוד.


## מה השתנה בנתונים

עברנו למקור Zenodo ברישיון CC BY 4.0 עם ייחוס. 389 רשומות אינן 389 אנשים; תיאור המקור מציין 245 משתתפים ואין מזהי אדם. קלט: prewk1, prewk2, prewk3, week1; יעד: האם week2 גדול מאפס. מאפייני טיפול, תגמולים, ציונים, דמוגרפיה וביקורים עתידיים אינם קלט.

היסטוריות זהות נשארות באותו חלק כדי שלא להעתיק אותו דפוס בין train ל־test. אין בכך הוכחה לעצמאות בין אנשים, והפיצול יוצר חלקים שונים בגודל ובשכיחות היעד. כדאי להציג גם Dummy ולהסביר מדוע דיוק לבדו מטעה.

Cursor הוא עורך הקוד; Git שומר גרסאות; GitHub שומר את הריפו ואת ה־PR. פותחים את תיקיית הפרויקט, משנים דבר שמבינים, בודקים ועושים commit עם תיאור מדויק. אין צורך להמציא שותפים או לפזר commits מלאכותיים. אפשר להסביר בכנות שנעזרנו בעוזר קוד ולדעת להסביר כל רכיב שנגיש.
