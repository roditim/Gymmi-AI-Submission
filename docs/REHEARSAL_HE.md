## הסיפור במשפט אחד

״Gymmi עוזר למתאמן לתכנן את השבוע, לסמן מה השלים ולראות התקדמות, עם יומן אישי שנשמר בענן ועוזר AI שמציע שיבוץ לפי זמינות בשפה חופשית.״

המוצר כרגע הוא יומן ותוכנית שהמשתמש מזין. עוזר AI מציע שיבוץ לאימונים שהמשתמש הזין, לפי זמינות בשפה חופשית. אין יצירת תרגילים ואין חיזוי השלמה. העיצוב מחזיר את כיוון ה־RPG בעזרת מסע שבועי וכרטיסי משימות. משימה היא אותו אימון ששמרנו ביומן; אין מאחוריה מערכת משחק נוספת או XP.

## ההדגמה באתר, צעד אחר צעד

1. פתח את הקישור הציבורי ולא localhost. אמור: ״זהו האתר שפרסמתי ל־Production ב־GitHub Pages.״
2. הירשם עם מייל שלך וסיסמה של לפחות 10 תווים. ב־MVP אין אישור מייל, ולכן הכניסה מיידית. אם כבר נרשמת, השתמש בכניסה. אל תציג את הסיסמה על המסך או בקוד.
3. בחר שבוע ריק ולחץ ״הוסף תוכנית לדוגמה״. הראה שאפשר לערוך שם, תאריך, דקות ופרטי אימון. התבנית אינה תוכנית שנוצרה ב־AI.
4. בחר אימון שתאריכו היום או בעבר וסמן ״הושלם״. אמור: ״זהו אותו סטטוס ביומן. המסך סופר אימון אחד שהושלם מתוך שלושה.״ אימון עתידי חסום לסימון; לכן בחר את התאריך מראש.
5. רענן את הדף. הראה שההשלמה נשארה, ואז פתח את ההיסטוריה.
6. פתח חלון גלישה נפרד או דפדפן אחר והיכנס לאותו חשבון. הראה שהיומן נטען מהענן. אם החלון כבר היה פתוח לפני השינוי, לחץ ״טען מחדש מהענן״. אין עדכון חי אוטומטי.
7. אם נשאר זמן, הראה ״הורד גיבוי JSON״. אפשר גם לבטל סימון ולהראות שהמונה חוזר לאפס.
8. סיים בהצגת קבצי הקוד המרכזיים. אין צורך להיכנס ללוח Supabase ולחשוף פרטי ניהול כדי להוכיח את המוצר.

## איך להסביר את הקוד בלי להסתבך

| קובץ | הסבר פשוט |
|---|---|
| docs/app/index.html | השלד: כותרות, טפסים, לחצנים ומקומות שבהם יוצגו האימונים |
| docs/app/style.css | המראה: צבעים, ריווח, לוח המשימות והתאמה לטלפון |
| docs/app/app.js | ההתנהגות: קורא את הטופס, בודק את הנתונים, מגיב ללחיצות ומעדכן את המסך |
| docs/app/ai.js | בקשת הצעת AI, הצגתה ואישור לפני שמירה |
| supabase/functions/ai-week-plan/ | אימות משתמש, מכסה, קריאת מודל ובדיקת ההצעה בצד השרת |
| docs/app/cloud.js | שתי פעולות מרכזיות: load קוראת את היומן ו־save שומרת אותו ב־Supabase |
| docs/app/config.js | כתובת השירות ומפתח publishable שמיועד להיות ציבורי |
| supabase/migrations/ | קובץ SQL שמגדיר טבלה וכללי גישה |

אימון הוא אובייקט עם id, תאריך, שם, דקות, פרטים, status וזמן סימון. state הוא העותק שבזיכרון הדפדפן. רשימת workouts שבתוכו היא יומן האימונים.

`validate` בודקת שהמידע מתאים למבנה, שאין מזהים כפולים ושמשך האימון והתאריך תקינים. `mark` משנה סטטוס. `save` בוחרת בין שמירה מקומית לענן וממתינה להצלחה. `render` מציירת מחדש את המסך ומחשבת את ההתקדמות. `changeAccount` מנקה את היומן המוצג לפני טעינת החשבון הבא, כדי שלא יופיעו נתוני החשבון הקודם.

ההתקדמות היא מספר ההשלמות בשבוע חלקי מספר האימונים בתוכנית השבועית. אימון שסומן כדילוג עדיין נמצא במכנה. זו התקדמות מול התוכנית המקורית, לא יחס הצלחה רק מתוך אימונים שכבר סומנו. כשאין אימונים מציגים אפס והסבר, ולא מחלקים באפס.

## איך Supabase עובד אצלנו

Supabase מספק שני חלקים שאנו משתמשים בהם: Auth ו־Postgres. Auth מטפל ברישום ובבדיקת הסיסמה. לאחר הכניסה הוא מחזיר Session, כלומר פרטי חיבור זמניים שמאפשרים לבקשות לזהות את המשתמש. הספרייה הרשמית מנהלת את ה־Session בדפדפן; לא כתבנו מנגנון סיסמאות משלנו.

במסד יש טבלה בשם workout_journals. לכל משתמש שורה אחת עם user_id, רשימת אימונים ב־JSON ומספר revision. בחרנו ביומן אחד כדי לשמור על אותו מבנה של מצב אורח ושל קובץ הגיבוי. זו בחירה פשוטה ל־MVP קטן; יש גבול של 1,000 אימונים ושל 1MB ליומן.

RLS היא בדיקת הרשאות בתוך המסד. התנאי המרכזי הוא `auth.uid() = user_id`: המשתמש המחובר יכול לקרוא ולעדכן רק את השורה שלו. גם אם מישהו משנה את ה־JavaScript או פונה ישירות ל־API, המסד ממשיך לבדוק את התנאי. זה נבדק בפועל בין שני חשבונות.

המפתח הציבורי באתר אינו מפתח מנהל. הוא מאפשר להגיע לשירות, אך ה־Session וכללי RLS קובעים לאילו נתונים מותר לגשת. מפתח service/secret וסיסמת המסד אינם חלק מהאתר או מהריפו. לעולם אל תראה אותם בהדגמה.

## מה קורה כשלוחצים ״הוסף אימון״

1. app.js קוראת את הטופס ומייצרת אובייקט אימון.
2. validate בודקת את הרשימה החדשה.
3. אם המשתמש אורח, שומרים ב־localStorage במכשיר. אם הוא מחובר, cloud.js שולחת את היומן ל־Supabase.
4. במסד, RLS בודקת בעלות. בבקשת עדכון נבדק גם שה־revision שקראנו עדיין זהה לגרסה במסד.
5. רק אחרי הצלחה מעדכנים את state ואת המסך. בכשל לא מציגים ״נשמר״ והטיוטה נשארת בטופס.

revision מגן מדריסה: אם מחשב קרא גרסה 2 וטלפון כבר שמר גרסה 3, המחשב אינו רשאי לשמור על בסיס גרסה 2. המשתמש טוען מחדש לפני המשך עריכה. זה אינו מיזוג אוטומטי.

## שאלות אפשריות ותשובות קצרות

**למה לא CrewAI?** ״בהבהרה האחרונה יונתן אמר שזה מומלץ ולא חובה, ושמודל מאומן אינו חובה. התמקדתי במוצר צר שעובד בקישור ציבורי. המחקר הקודם נשמר בנפרד ואינו מופעל באתר.״

**איפה ה־AI במוצר?** ״זה שם הרעיון המקורי, וכעת יש באתר עוזר AI אמיתי שמפרש זמינות ומציע שיבוץ. הוא אינו מייצר תרגילים או חוזה השלמה.״

**איפה ה־RPG?** ״כרגע בעיצוב: מסע שבועי, לוח משימות ותגיות השלמה. הדמויות, XP והרמות הם הרחבה עתידית.״

**מי המשתמש?** ״המתאמן שמארגן את השבוע שלו. כרגע אין חשבון מנהל חדר כושר או מערכת ניהול לקוחות.״

**האם התוכנית מותאמת אישית?** ״המשתמש מזין או עורך את התוכנית שלו, למשל תוכנית שקיבל ממאמן. זו אינה יצירה אוטומטית או התאמה רפואית.״

**למה אין שרת Python?** ״הממשק סטטי, והלוגיקה הפשוטה רצה בדפדפן. Supabase מספק את שירות ההתחברות והמסד. GitHub Pages מגיש את קבצי האתר.״

**מה ההבדל בין אורח לחשבון?** ״אורח שומר רק בדפדפן. חשבון שומר בענן. היומן המקומי אינו עולה אוטומטית; אפשר להעבירו בלחיצה עם אישור.״

**מה עוד חסר?** ״אין אימות בעלות על מייל או שחזור סיסמה, ואין סנכרון בזמן אמת. ההרשמה ללא אימות אושרה במפורש ל־MVP הלימודי. מסלול Free עשוי להשהות את הפרויקט אחרי תקופה של פעילות נמוכה.״

**איך בדקת?** ״הרצתי בדיקות דפדפן למצב אורח, ענן והרשמה. הן כוללות רענון, דפדפן נוסף, בקשות API מחשבון אחר וכשל רשת. אלה קבוצות תרחישים שבוצעו בפועל, לא משתמשים אמיתיים ולא מדדי ML.״

**האם כתבת לבד?** ״נעזרתי בעוזר קוד בפיתוח ובבדיקות. אני אחראי להבין ולהסביר את הקוד, ולכן שמרתי על פונקציות פשוטות ועל היקף קטן.״
